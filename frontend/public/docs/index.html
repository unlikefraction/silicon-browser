Use Browser.
Build on Browser.

Managed browser profiles, shared sessions, live handoff, recordings, search, and fetch. Start with the CLI; use the website for interactive work and the stateless Rust client for applications.

These instructions are the starting point. Read the full CLI guide as Markdown or explore any command with --help.

1. Install

On macOS or Linux, run the one-line installer. It selects your architecture, verifies the download, and installs browser into ~/.local/bin. Linux requires glibc 2.34 or later; macOS and Linux support ARM64 and x86-64.

The command below installs without authentication. Sign in separately with browser login and run browser setup when ready to configure browser control and recording delivery. Source installation needs Rust 1.98 or later:

cargo install silicon-browser-cli --version 0.2.4 --locked
browser --help
browser iam --json

2. Authenticate with IAM

Browser uses short-lived authorization tokens from the official IAM CLI or IAM's web consent screen. It never asks for your IAM password. Replace tos with your organization:

slt=$(iam login --app-id 'browser' --grant-org tos -o json | jq -r .slt)
browser --org-id tos login "$slt"
browser login status --json
browser setup

Setup installs the pinned native browser controller and requests a separate fresh IAM token for background recording authorization. Browser can then deliver completed recordings after your terminal closes. browser iam --json identifies the application as browser.

Private state lives in $SILICON_HOME/.silicon-browser, or ~/.silicon-browser when SILICON_HOME is absent. State is partitioned by backend URL and testing environment. SB_HOME explicitly selects a different private home.

3. Run a browser

browser profile ls
browser session new PROFILE_ID --name "Research" --description "Compare vendors" --ttl 30m
browser run SESSION_ID "open https://example.com"
browser run SESSION_ID "snapshot -i"
browser run SESSION_ID "screenshot ./research.png"
browser session end SESSION_ID --note "done"

Use browser profile new --help to create a reusable profile, or browser session new --incognito for a one-off session. Browser actions execute on your machine through a direct remote-browser connection. Screenshots and downloads write locally; completed session recordings go to your authorized Briefcase.

Search and fetch do not require a browser session:

browser search "browser automation" --purpose "Find primary sources"
browser fetch https://example.com --purpose "Extract relevant claims"

Use an IAM testing environment

Create a Browser test application and actors in IAM. Browser accepts that application's ask_ secret and asks IAM to identify and verify the environment. An IAM root key is optional. The app secret is test configuration; production login still requires a short-lived token.

CLI

Keep the secret in a private JSON file containing {"app_secret":"ask_..."}, then enroll it:

browser testing login --credentials-stdin < test-credentials.json
# Use the environment UUID returned above on every test command.
browser --test ENVIRONMENT_UUID --org-id tos login si:worker
browser --test ENVIRONMENT_UUID testing status --json
browser --test ENVIRONMENT_UUID login status --json
browser --test ENVIRONMENT_UUID profile ls

browser testing login also reads SB_TEST_APP_SECRET. Test login accepts an existing test actor ID such as c:alice or si:worker, or an IAM test oac_ token. Mint a short-lived test token with iam --test ENVIRONMENT_UUID login --app-id 'browser' --grant-org tos -o json.

Browser sessions require test recording storage. Add briefcase_test_environment_key to the enrollment JSON (or set SB_BRIEFCASE_TEST_KEY) using the Briefcase app secret imported into this same IAM environment. Run browser --test ENVIRONMENT_UUID setup to authorize recording delivery as the signed-in actor. Missing storage or authorization fails explicitly.

Website

  1. Open Browser and select Testing environment on the welcome screen or workspace header.
  2. Enter the test app secret, an actor ID or test short-lived token, and its organization. Add the imported Briefcase test app secret to create browser sessions.
  3. Select Enter test mode. The badge shows the verified environment name and UUID.
  4. In Settings, enable recording access using that test actor or a fresh test token.
  5. Select Exit test mode to restore your production workspace. Reloading also clears the test sign-in.

Website test credentials stay in memory and never enter localStorage or sessionStorage. Browser data is isolated by verified IAM environment UUID and clean generation. Cleaning IAM selects fresh Browser data; rotating the app secret preserves the current generation. Invalid or missing test credentials never fall back to production. Tests use the normal API and real, metered browser/search providers.

Call the testing API

Use the same business routes as production, beneath a verified test environment prefix. Responses use {"data": ...}; failures return an error object with a code, message, and request ID where available. Keep secrets out of URLs and logs.

1. Verify the test app secret

POST https://backend.browser.teamofsilicons.com/api/v1/testing/context
Content-Type: application/json

{"app_secret":"ask_..."}

IAM verifies that the secret belongs to the Browser test application. The response identifies its environment:

{"data":{"environment_id":"ENVIRONMENT_UUID","app_id":"browser","name":"My test environment"}}

The JSON may additionally include iam_test_key and briefcase_test_environment_key. The optional iam_test_key is exactly 32 ASCII letters or digits. briefcase_test_environment_key contains the imported Briefcase IAM app secret (ask_ plus 43 base64url characters). Both must belong to the Browser app secret’s IAM environment; existing field names are retained for compatibility.

2. Authenticate a test actor

POST https://backend.browser.teamofsilicons.com/testing/ENVIRONMENT_UUID/api/v1/auth/exchange
Content-Type: application/json
x-sb-test-app-secret: ask_...

{"short_lived_token":"si:worker","org_id":"tos"}

The exchange returns data.access_token, data.refresh_token, data.expires_at, identity, and organization. The actor must exist in this IAM environment. You may supply an IAM test short-lived token instead of an actor ID.

3. Call the normal API in that environment

GET https://backend.browser.teamofsilicons.com/testing/ENVIRONMENT_UUID/api/v1/profiles
Authorization: Bearer oat_...
X-Org-Id: tos
x-sb-test-app-secret: ask_...
HeaderPurpose
x-sb-test-app-secretRequired on every test request. IAM verifies the environment; the URL UUID must match.
Authorization and X-Org-IdRequired for authenticated operations. The test app secret does not replace the actor's bearer token.
x-testing-environment-keyOptional IAM root key for the same environment.
x-sb-test-briefcase-keyPaired Briefcase test configuration for recording storage. Supply it when enrolling through the API and retain it on requests that configure test storage.

Refresh with POST /testing/ENVIRONMENT_UUID/api/v1/auth/refresh, JSON {"refresh_token":"ort_...","org_id":"tos"}, and the same test headers. Keep the test prefix and credentials on exchange, refresh, and subsequent calls. Never retry a rejected test request against production.

Explore the command tree

browser
├── iam --json
├── login <SLT> / login status --json
├── testing login / testing status --json
├── setup
├── profile {ls,show,new,set,end}
├── proxy ls
├── session {new,ls,show,live,logs,sync,end}
├── run <session-id> <browser-command>
├── recording {ls,show,send,rm}
├── usage {limits,ls,show}
├── search / fetch
└── report-bug --title <text> --details <text> [--pr <ref>]

Use browser session --help, browser run --help, or browser --help search-and-fetch to go deeper. Use --json for structured agent output. Command reports retry without repeating the browser action; browser session sync SESSION_ID flushes queued reports.

To report a reproducible defect, use browser report-bug. Include the failing command, expected and actual behavior, and relevant redacted diagnostics. If you have already patched it, attach the pull request with --pr.

Build on Browser

The stateless silicon-browser Rust package implements the API client. The silicon-browser-cli package provides browser; silicon-browser-shared contains the common contracts.

cargo add silicon-browser@0.2.4

# In a source checkout:
cargo test --workspace --all-targets
npm ci --prefix frontend
npm test --prefix frontend
npm run build --prefix frontend

Test integrations through the IAM environment flow above. It runs the production handlers with separate authentication and storage. For architecture, deployment, recording requirements, and current limits, follow the informative references:

One-line setup

Install the CLI without authentication. Then follow the separate sign-in and setup instructions above.

curl -fsSL https://raw.githubusercontent.com/unlikefraction/silicon-browser/managed-v0.2.4/scripts/install.sh | sh -s -- --no-setup && export PATH="$HOME/.local/bin:$PATH"
